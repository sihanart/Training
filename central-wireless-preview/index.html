01

สถาปัตยกรรม CNX

Cloud-managed wireless — Central ดูแล config และ authentication ส่วน traffic ของผู้ใช้ออก Internet ที่ไซต์โดยตรง

① Control plane อยู่บน cloud

Config, firmware, monitoring, floorplan และ report ทำจาก Central ทั้งหมด ไม่มีตัวจัดการที่ไซต์

② NAC ก็อยู่บน cloud

Central NAC เป็น RADIUS ให้เลย — MAC Auth, Guest portal และ 802.1X ที่ผูกกับ Entra ID โดยไม่ต้องตั้ง ClearPass ที่ไซต์

③ Data plane อยู่ที่ไซต์

AP bridge traffic ลง VLAN ที่ไซต์แล้วออก Internet ที่นั่น — เป็นจุดต่างสำคัญจากสถาปัตยกรรม controller แบบเดิม

02

Lab topology (แบ่งตาม Pod)

Pod ละ 2–3 คน แต่ละ Pod ได้ Configuration Group + Site ของตัวเองบน Central และ SSID คนละชุด เพื่อให้ config ทับกันไม่ได้

Lab 0–2 — ทำบน Central ล้วน

เพิ่มอุปกรณ์, ผูก license, สร้าง Configuration Group และ Site, ตรวจ firmware compliance — ยังไม่ต้องแตะ CLI ของ AP เลย

Lab 3 — WLAN + Authentication

สร้าง 3 SSID ต่อ Pod: PSK + MAC Auth, Guest self-registration และ 802.1X ที่ผูกกับ Entra ID พร้อม role-based firewall

Lab 4–7 — Day-2 operations

Monitoring, Floorplan, Reporting และ WLAN tuning ทำจาก Central ทั้งหมด ใช้ข้อมูล telemetry ที่ AP ส่งขึ้น cloud

03

แผน SSID / VLAN

n คือหมายเลข Pod — Pod 1 ใช้ VLAN 11–14 กับ 10.1.x.0/24, Pod 2 ใช้ VLAN 21–24 กับ 10.2.x.0/24 ไล่ไปเรื่อยๆ

VLANชื่อ / การใช้งานSubnetหมายเหตุ
n1MGMT — AP / Switch10.n.1.0/24AP รับ IP แล้วโทรออกหา Central เอง
n2WLAN Employee — 802.1X10.n.2.0/24SSID PODn-EMP · Cloud NAC + Entra ID (Lab 3.3)
n3WLAN Guest — Self-registration10.n.3.0/24SSID PODn-GUEST · Portal โฮสต์บน Central (Lab 3.2)
n4WLAN IoT — PSK + MAC Auth10.n.4.0/24SSID PODn-IOT · ใช้สอน MAC Authentication (Lab 3.1)
100Transit / Internet uplink192.168.100.0/24Default route → 192.168.100.254
200Services192.168.200.0/24DHCP/DNS 192.168.200.30 — ไม่ต้องมี NAC on-prem

ทุก SSID เป็น **Bridge mode** — client ได้ IP จาก DHCP ที่ไซต์และออก Internet ผ่าน gateway ที่ไซต์ ไม่มี tunnel ขึ้น cloud ดังนั้น VLAN ต้อง trunk มาถึงพอร์ตที่ต่อ AP
